1. EXECUTIVE SUMMARY & PROBLEM STATEMENT
================================================================================
The primary goal was to achieve seamless "Spotify Connect" style synchronization 
between the Sangita Web Client (desktop/laptop browser) and the Sangita Native 
Android Application (POCO F7).

Specific User Expectations:
1. Start playing a track on the phone -> open the website on desktop -> the website 
   immediately shows the same track, position, and playing status.
2. Transfer/switch playback to the browser -> browser begins outputting audio 
   instantly from the exact handoff timestamp without freezing or restarting from 0.
3. Control playback interchangeably (phone controls browser, browser controls phone) 
   with zero audio stutter, zero lag, and synchronized real-time lyrics.
4. When browsing/switching pages on either device, no 2-3x refresh loops or navigation 
   freezes should occur.

Observed Reality & Failures:
- Phone and web showed 10-15 second desynchronization. Phone indicated the track was 
  playing and advancing while the browser was still waiting for audio buffer chunks.
- When transferring playback from phone to browser, the browser became marked as 
  "active", the phone stopped playing audio, but NO AUDIO ever played from the browser. 
  Both devices were effectively silent.
- When opening the website while the phone was already playing, the track was not 
  consistently loaded into the browser audio element or queue.
- Lyrics on the phone lagged behind the actual audio and behind the web player by up 
  to 1 full second.

5. DEEP ARCHITECTURAL BREAKDOWN: SYNC SERVER & REDIS
================================================================================
Source Files:
- e:\sangita-main\sync-server\server.js

How the Sync Server Works:
1. Framework: Node.js Express + Socket.IO server running on port 3001.
2. Storage: Redis key-value store.
   - `sangita:sync:${userId}:devices`: Redis SET storing active device IDs.
   - `sangita:sync:${userId}:device:${deviceId}`: Redis HASH with TTL (120s) storing socketId, name, type.
   - `sangita:sync:${userId}:state`: Redis HASH storing `trackId`, `positionMs`, `durationMs`, `isPlaying`, `activeDeviceId`, `updatedAt`.
3. Event Multiplexing:
   - When a client sends `PLAYBACK_STATE_CHANGED`, server saves to Redis and broadcasts to `io.to(userRoom).emit('PLAYBACK_STATE_CHANGED', state)`.
   - When a client sends `TRANSFER_PLAYBACK`, server updates `activeDeviceId` and broadcasts state.
   - When a client sends `REMOTE_CONTROL`, server looks up `state.activeDeviceId` in Redis, retrieves its `socketId`, and routes `REMOTE_COMMAND` directly to that socket.

6. CHRONOLOGICAL LOG OF ALL ATTEMPTS & WHY THEY FAILED
================================================================================

Attempt 1: Bidirectional State Broadcasting without Source Filtering
- Goal: Broadcast every play/pause/seek from both devices to keep them mirrored.
- Result: Catastrophic Echo Loop. Device A emitted state -> Server relayed to Room -> 
  Device B received state -> Device B updated its player -> Device B's player listener 
  triggered another broadcast -> Echo loop flooded Socket.IO and caused constant 
  stuttering and playback pauses.

Attempt 2: Adding Active Device Master-Slave Flag
- Goal: Only the device flagged as `activeDeviceId` broadcasts; other devices only listen.
- Result: Stale Active Device Deadlocks. When the phone disconnected or went to sleep, 
  the web app refused to take control because it believed the phone was still active. 
  When web attempted to take control, the phone woke up and immediately claimed back 
  active status, fighting for control.

Attempt 3: Remote Track Delegation via REMOTE_CONTROL ("play_track")
- Goal: When phone changes songs while Web is active, phone sends `{ action: 'play_track', payload: { path } }` 
  to the web browser instead of hijacking local sound.
- Result: Web Queue Desync. The browser received `play_track`, but because the track was 
  not in the browser's current active playlist/queue, `playTrackRef.current` looked for the 
  track in `q`, could not find it, and failed to play.

Attempt 4: Progress Polling & Buffering State
- Goal: Keep position sliders and lyrics in sync.
- Result: The 10-Second Desync Bug.
  When Web clicked play, it immediately broadcasted `isPlaying = true` while HTML5 `<audio>` 
  was still fetching large FLAC audio chunks from the backend. The observing phone received 
  `isPlaying = true` and started advancing its slider and lyrics 10 to 15 seconds BEFORE 
  the browser produced a single sound.

Attempt 5: Lyrics Delay on Phone
- Goal: Synchronize lyrics highlight on phone.
- Result: 1,000ms delay. The phone's `PlaybackController` progress polling coroutine was 
  hardcoded to `delay(1000)`. Position only refreshed once a second, meaning active lyrics 
  jumped in coarse 1-second chunks, lagging behind both audio and web.

7. THE CORE ROOT CAUSES UNCOVERED
================================================================================

--------------------------------------------------------------------------------
7.1 Root Cause #1: Browser Autoplay Security Policy
--------------------------------------------------------------------------------
Why it happened:
When a user is playing a song on their phone and clicks "Transfer to Web Browser", 
the sync server emits `REMOTE_COMMAND: play` or `PLAYBACK_STATE_CHANGED: activeDeviceId=web`.
The web browser receives this message over the WebSocket connection.
In JavaScript:
```javascript
audio.play().catch(err => {
  // Throws: NotAllowedError: play() failed because the user didn't interact with the document first.
});
```
Browsers deliberately disallow web pages from producing audio unless the user has 
actively clicked inside that browser tab during that session.
Because the transfer was initiated remotely from the PHONE, the browser had received 
NO user gesture in that tab. The browser silently blocked audio playback.
The phone paused its sound (because it yielded to the web), while the web was blocked 
by the browser security sandbox. Both devices ended up completely muted.

--------------------------------------------------------------------------------
7.2 Root Cause #2: Web Queue Desynchronization (Empty Queue)
--------------------------------------------------------------------------------
Why it happened:
In `frontend/src/App.jsx`:
```javascript
const { q, idx } = getActiveQueueAndIndex();
if (q.length === 0) return; // <-- SILENT ABORT
```
When a user launches the web application while a track is already playing on the phone:
- The website loads its UI, but the user has NOT clicked any playlist yet.
- Therefore, the web app's internal `queue` state is completely empty: `[]`.
- `loadedTrackIdRef.current` is `null`.
- When the phone sends a `play`, `togglePlay`, or `transfer` command to the web, 
  the web app checks `q.length === 0` and silently exits. It does not synthesize 
  a track object or load `audio.src`.

--------------------------------------------------------------------------------
7.3 Root Cause #3: State Handshake Ping-Pong & Feedback Relay Loops
--------------------------------------------------------------------------------
Why it happened:
Socket.IO room `io.to(userRoom).emit('PLAYBACK_STATE_CHANGED')` broadcasts to ALL 
sockets connected to that user account, including the socket that originated the event.
If the originating device re-applies the incoming event to its own state, it re-triggers 
player event listeners (`onIsPlayingChanged`, `onPositionDiscontinuity`), creating a 
continuous loop of re-broadcasts.

--------------------------------------------------------------------------------
7.4 Root Cause #4: Buffering vs Playing Semantic Mismatch
--------------------------------------------------------------------------------
Why it happened:
In web audio, setting `audio.src = url` and calling `audio.play()` does NOT mean audio 
is playing. The browser must first negotiate HTTP range headers, receive sufficient audio 
packets, and decode the stream. This takes 2 to 12 seconds depending on network speed.
Broadcasting `isPlaying = true` immediately at the time `audio.play()` is called causes 
every other device to assume sound is already playing, advancing their lyrics and clocks prematurely.

--------------------------------------------------------------------------------
7.5 Root Cause #5: Progress Polling Frequency & Latency
--------------------------------------------------------------------------------
Why it happened:
The Android player polling ran at 1 Hz (`delay(1000)`). High-definition lyrics synchronization 
requires at least 10 Hz (100 ms) polling combined with lookahead compensation for the 
Android `AudioTrack` hardware buffer (~150-250ms).

9. DEFINITIVE ENGINEERING BLUEPRINT TO PERMANENTLY RESOLVE SYNC
================================================================================

To achieve flawless, 100% reliable Spotify-Connect synchronization across Web and Android, 
the following 4 architectural rules MUST be strictly enforced:

RULE 1: Explicit User Gesture Handoff on Browser (Addressing Autoplay Policy)
- When playback is transferred to Web Browser, if the browser tab does NOT have active 
  user interaction permissions, the browser MUST NOT attempt a silent `audio.play()` 
  that will be rejected by Chrome/Firefox.
- Instead, the Web Player UI must render a prominent, glowing banner:
  "🎵 Playing on Web — Click to Listen Here"
- Clicking that banner fulfills the browser's user-gesture security requirement, instantly 
  unlocking audio output without error.

RULE 2: Standalone Track Synthesis (Addressing Empty Queue)
- When Web receives a remote command or state update for a track that is NOT currently 
  in its local playlist queue, Web must immediately synthesize a standalone Track object 
  from the path, set `audio.src = /api/stream/{path}?token={token}`, set `currentTime = positionMs / 1000`, 
  and stage the audio element before attempting playback.

RULE 3: Buffer-Guarded Playback State (Addressing 10s Desync)
- Neither Android nor Web may ever broadcast `isPlaying = true` while their media engines 
  are in a buffering or loading state.
- Android: Broadcast `isPlaying = true` ONLY when ExoPlayer reaches `Player.STATE_READY` 
  AND `player.isPlaying == true`.
- Web: Broadcast `isPlaying = true` ONLY when the `<audio>` element fires the `'playing'` event. 
  Broadcast `isPlaying = false, isBuffering = true` on the `'waiting'` event.

RULE 4: Targeted Direct-Route Remote Commands (Addressing Echo Loops)
- Every `REMOTE_CONTROL` payload must include `targetDeviceId`.
- If a client receives a `REMOTE_COMMAND` whose `targetDeviceId` does not match its own 
  device ID, it MUST discard it immediately.
- The sync server must never multicast a remote command back to the socket that sent it.
