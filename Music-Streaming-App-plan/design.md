# Architecture and product design

## Scope
A user signs in on Android and web, listens using an authorized provider, and continues on another device at the last saved position. An administrator sees usage across users, subject to clearly disclosed consent and access controls. Keep existing Android features intact; build browser equivalents where technically and legally feasible, tracking exceptions. Local files and downloads may not exist on another device and must never be uploaded implicitly.

## Proposed system
Android (Media3 player, Room and DataStore) and responsive browser (HTML audio/provider SDK) communicate over HTTPS with a versioned API. The API owns accounts, devices, handoff state, consent, listening events and aggregates in PostgreSQL. Authorized catalog adapters provide metadata and playable URLs or approved embeds; their licenses and playback restrictions govern each client. Docker Compose runs API, database and web/reverse proxy; persisted database volume, migrations, health checks and backups are mandatory. Avoid proxying, downloading or transcoding audio without explicit rights. Browser authentication/CORS, expiring signed URLs and provider restrictions need proof of concept first.

## Identity and authorization
Use individual accounts and roles (`user`, `admin`), with server-side authorization on every endpoint and object. Plan email/password authentication with Argon2id, email verification/reset via configured mail service, revocable sessions and rotation; exact onboarding and first-admin provisioning require operator decision. Browser uses secure HttpOnly SameSite cookies and CSRF protection; Android uses short-lived access credentials with rotating refresh tokens stored in platform-protected storage. Require TLS in production; rate-limit login and resets, prevent account enumeration, revoke sessions on password change. Admin role cannot be self-assigned; audit grants and access. Avoid promising zero admin visibility: admin access is an explicit product feature.

## Playback handoff
Server keeps one current checkpoint per account: provider and stable track ID, playback position, paused/playing state, duration if known, timestamp, device ID and revision. On track change, pause, seek and periodic bounded intervals, client sends an authenticated idempotent checkpoint. Server orders changes by server-assigned revision and optimistic concurrency, not client wall clocks. Reconnect fetches latest state; do not autoplay without user interaction where browser policy forbids it. Show the source device, timestamp and a Continue action; handle unavailable tracks, expired URLs, offline devices and conflicts. Default is manual handoff and a single active controller, with no audio transfer or tight simultaneous sync. Local offline writes queue with bounded retention; stale queued checkpoints must not overwrite newer revisions. Server stores IDs, never expiring playback URLs or secrets. Test seek, end, restart, rapid device switching and offline recovery.

## Listening analytics
On-device player emits explicit start, progress/heartbeat, pause, resume, seek, end and like/unlike events. Record event UUID, account/device, session ID, provider/track ID, event type, playback position, occurred time, server receive time, schema version and for progress a bounded played-duration delta. Do not infer listening from wall-clock time while paused or count seek jumps; account for speed and duplicate/retry events. Deduplicate UUIDs and cap suspicious intervals; distinguish offline estimates. A user/device overlap can produce separate device time; define aggregate semantics visibly. Collect only after consent; add durable outbox, retries and deletion on withdrawal. Use server-derived daily aggregates per configured reporting timezone with UTC event timestamps; handle DST and late arrivals with recomputation. Define likes as current explicit user action, and show both unique users and actions if relevant. Genres come from provider metadata and may be unknown or multiple; label source and avoid inventing categories.

Dashboard: date range, daily listening duration, top tracks/artists, genre distribution, user/device breakdown and per-user detail for authorized admins; filters, empty states and time-zone labeling. User-facing privacy page explains collection, admin access, retention, deletion and contact. Exports require authorization, audit and safe handling. No secret or raw personal data in sample fixtures.

## Data and contracts
Initial tables: users, roles, sessions/refresh tokens, devices, consent records, track metadata/provider IDs, playback checkpoints, listening events, likes, daily aggregates and admin audit events. Use UUIDs, foreign keys, tenant/user constraints, indexes on user/time and provider IDs, unique event IDs and reversible versioned migrations. Set retention as operator configuration with explicit policy, not a guessed legal requirement; delete both raw records and derived aggregates when required, with backup expiry policy.

Proposed `/api/v1`: auth/register, login, refresh, logout, password reset; `/me`, `/me/consent`, `/me/export`, `/me` deletion; `/devices`; `/playback/checkpoint` GET/PUT with revision; `/events/batch`; `/likes`; `/catalog/search` and provider playback resolution; `/admin/analytics` and audited user drill-down. Define request/response schemas, validation, pagination, stable error codes, idempotency and authorization in OpenAPI before implementation. No endpoint accepts a client-supplied user ID as authority.

## UI and operations
Android additions fit its existing Nothing OS design and keep offline/guest behavior unless product decisions change it. Web follows a compatible minimal visual language, responsive navigation, keyboard and screen-reader support, high contrast and reduced-motion preferences. Provide sign-in, consent, playback, library, settings, continuation prompt and administrator dashboard. Surface consent and connectivity states without blocking local listening unnecessarily.

For development, Compose uses isolated network, environment template and persisted Postgres volume. Production configuration requires TLS reverse proxy, strong externally supplied secrets, backups and tested restore, upgrades and rollback, resource limits, monitoring, retention jobs and least privilege. Do not expose database port publicly. Test restore to a separate instance; document recovery objectives rather than claiming a backup is sufficient.

## Existing implementation assumptions — verify with user before relying on them
- **Music Source:** A prior document mentions free API wrappers. Free access alone does not establish permission to stream. The user explicitly chose a source we have permission to stream; select and verify one before using it.
- **Admin Provisioning:** First registered user through the setup flow is automatically granted the `admin` role.
- **User Onboarding / Signup:** Admin-invite only. Subsequent user accounts can only be created by an administrator via the Admin Dashboard.
- **Telemetry Retention:** Indefinite retention for raw listening event logs until the user explicitly revokes consent or triggers account deletion.
- **Reporting Timezone:** `Asia/Kolkata` (IST, UTC+5:30) as the primary timezone for calendar-day aggregation rollups.
- **Hosting & Topology:** Root Docker Compose with isolated bridge network, PostgreSQL 16 (persisted volume), Fastify Node.js/TypeScript API (`server/`), and React TypeScript SPA with Nginx reverse proxy (`web/`).



## Web product and visual acceptance standard
Web should provide the complete Android user-facing feature set wherever browser capabilities and content rights permit, with usable responsive equivalents rather than a sparse dashboard. Start from the Android screenshots in `android/Screenshots/`, upstream `DESIGN.md`, actual Compose screens and feature ledger. Compare the primary navigation, artwork, content density, hierarchy, player, lyrics, queue, library, search and settings in real usage. Derive a consistent token and component system (typography, spacing, artwork ratios, color, states and motion); maintain the visual quality and musical character of Android while adapting layouts to desktop and touch devices. Do not merely copy labels or default card layouts.

Design desktop, tablet and mobile navigation, a persistent functional player and detailed now-playing surface; make queue, lyrics, playback controls and discovery accessible without overlapping content. Accommodate varied artwork, long names, empty libraries, loading, API errors and unavailable tracks. Use semantic controls, visible focus, keyboard support, labels, contrast and reduced motion. Test at representative narrow and wide viewports using the actual running app. Document browser-only limitations and any provider restrictions beside the relevant feature. No mock content in production-facing flows.

Audit existing web implementations: `web/src/stores/sampleTracks.ts` and `HomeView.tsx` include sample fallback content; `server/src/routes/v1/catalog.ts` includes curated metadata and search-based stream resolution. These are starting observations, not verified real catalog data or licenses. Replace misleading behavior with verified integrations and honest states; keep fixtures only in explicit test/demo mode.
